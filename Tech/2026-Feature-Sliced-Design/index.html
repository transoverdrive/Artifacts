Feature-Sliced Design (FSD)

프론트엔드 폴더 정리 규칙 — "코드를 어디에 두는가"를 팀원·AI와 합의하는 언어. React / React Native / Expo 공통.

30초 요약 · 폴더 예시 · 7 레이어 · 2대 규칙 · 흔한 실수 · 점진 도입 · RN/Expo · AI 지시문 · 핵심 링크

30초 요약

  • 코드를 Layers(영향 범위) → Slices(업무 도메인) → Segments(기술 목적) 3겹으로 나눈다.
  • 프레임워크·언어 무관. 앱이 아니라 애플리케이션을 만들 때 쓴다 (라이브러리용 아님).
  • 작은 앱은 app+pages+shared 3층으로 시작, 필요할 때 추가.
  • 공식 문서의 첫 충고: 멀쩡한 구조는 뜯지 마라. 새 멤버 적응이 느리거나, 무관한 수정이 연쇄 파손될 때만 도입.

폴더 예시

src/
├── app/          앱 전체 (라우터·프로바이더·전역 설정)
├── pages/feed/   화면 = slice (도메인 단위)
│   ├── ui/       화면 부품        ← segments (목적별)
│   ├── api/      서버 통신
│   └── model/    상태·검증·스키마
├── features/     좋아요·댓글·로그인 (사용자 액션)
├── entities/     user·post·product (업무 개념)
├── widgets/      여러 화면 공용 큰 UI (헤더·탭바)
└── shared/       UI킷·API클라이언트·공용 lib·config

7 레이어 (위 → 아래)

레이어담는 것
app라우터 설정·프로바이더·전역 스타일·진입점·글로벌 store 설정
processes폐기 예정 — 사용 금지. features·app으로
pages화면(screen). 1화면=1slice. 재사용 안 되는 UI는 여기 둬도 됨
widgets여러 화면에서 쓰는 큰 UI 블록. 중첩 라우터에선 라우터 블록 자리
features사용자가 하는 액션. 여러 화면 재사용되는 것만 (남발 금지)
entitiesuser·post 같은 업무 개념 + 표시용 UI + 검증 스키마
sharedUI킷·API클라이언트·lib·config·i18n·route 상수. 비즈니스 로직 없음

딱 2대 규칙

규칙 1 — import rule: 위 레이어는 strictly 아래 레이어만 import. 같은 층끼리 금지.
예: features/aaa는 features/bbb 불가, entities·shared는 가능. 예외 app·shared는 내부 segment끼리 자유.
규칙 2 — public API: slice 바깥은 slice의 index.ts로만 import (내부 구조 직접 참조 금지).
pages/feed/index.ts → export { FeedPage } from "./ui/FeedPage". 바깥 계약만 지키면 내부는 맘대로 뜯어고쳐도 됨.

세그먼트 이름 짓기

관용 이름: ui · api · model · lib · config. 이름은 목적(why)으로. components·hooks·types·utils 같은 본질(what) 이름은 금지 — 무관한 코드가 뭉쳐 리팩터링이 깨진다.

entity끼리 알면 @x로 드러내기: entities/A/@x/B.ts ("A crossed with B"). 몰래 import 말고 연결을 눈에 보이게. Entities에서만, 최소 사용.

흔한 실수 5

  1. Shared 비대화 — Shared는 계획 말고 개발 중 "진짜 공유되는 것만" 추출. 의존자가 많아 수정 파급이 큼.
  2. 페이지 중복 무리한 추상화 — 복붙은 architecturally wrong이 아님. 단 비즈니스 로직 복붙은 금지.
  3. Feature 남발 — 신입이 pages+features만 봐도 앱 기능이 보여야 함.
  4. export * — slice 인터페이스 파악 불가 + 내부 노출. 필요한 것만 명시 export.
  5. barrel(index) 함정 — 순환 import(같은 slice 안은 상대경로로 해결) · shared/ui 트리쉐이킹 파괴(컴포넌트별 index 분리) · IDE 자동import 경로 틀어짐(Steiger 린터로 단속).

기존 프로젝트 점진 도입 (8단계 요약)

  1. 페이지로 나누기 (route 얇게, page 두껍게)
  2. 페이지 외 분리 → shared / app
  3. 페이지 간 cross-import 제거 (복붙 or shared행)
  4. Shared 털기 (한 화면 전용은 page slice로)
  5. 목적별 정리 (components→shared/ui, utils→shared/lib, constants→shared/config)
  6. (선택) 공용 Redux slice → entities / features
  7. (선택) modules 폴더 → features or widgets
  8. (선택) shared/ui에서 비즈니스 로직 분리 → 순수 UI킷
팀·매니저 설득 먼저. 셀링 포인트: 점진적이라 새 기능 개발이 중단되지 않음 + 문서화된 구조라新人 온보딩 단축.

AI에게 시킬 말 (복붙용)

"이 레포 FSD import rule 위반 찾아줘 (같은 층·위층 import 목록으로)."
"신규 기능 X를 features/X slice로: ui/api/model + index.ts public API."
"shared 중 한 화면 전용 찾아서 해당 page slice로 옮겨줘."
"components/utils/hooks 폴더 있으면 목적명 세그먼트로 재구성해줘."
