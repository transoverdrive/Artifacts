Feature-Sliced Design (FSD)

프론트엔드 폴더 정리 규칙 — "코드를 어디에 두는가"를 팀원·AI와 합의하는 언어. React / React Native / Expo 공통.

30초 요약

  • 코드를 Layers(영향 범위) → Slices(업무 도메인) → Segments(기술 목적) 3겹으로 나눈다.
  • 프레임워크·언어 무관. 앱이 아니라 애플리케이션을 만들 때 쓴다 (라이브러리용 아님).
  • 작은 앱은 app+pages+shared 3층으로 시작, 필요할 때 추가.
  • 공식 문서의 첫 충고: 멀쩡한 구조는 뜯지 마라. 새 멤버 적응이 느리거나, 무관한 수정이 연쇄 파손될 때만 도입.

왜 필요한가 — PM이 느낄 통증

규모가 커진 프론트엔드에서 흔한 장면: "A 화면 고쳤더니 B 기능이 깨졌다", "신입이 2주째 코드 위치를 못 찾는다", "새 기능 하나에 손댈 곳이 열 군데". FSD는 이 통증의 처방전이다. 코드를 영향 범위(어디까지 파급되나), 업무 도메인(무슨 일용 코드인가), 기술 목적(화면용? 서버용? 설정용?)으로 나눠, 수정 파급을 눈에 보이게 가둔다.

다만 공식 문서가 못 박듯, 지금 구조가 멀쩡하면 도입 비용(학습+마이그레이션)이 이득보다 크다. 전환 설득용 논리 3개: ① 점진적이라 새 기능 개발 중단 없음 ② 신입 온보딩 단축 ③ 문서화된 구조라 자체 문서 유지비 절감.

3겹 구조 — Layers → Slices → Segments

src/
├── app/          앱 전체 (라우터·프로바이더·전역 설정)
├── pages/feed/   화면 = slice (도메인 단위)
│   ├── ui/       화면 부품        ← segments (목적별)
│   ├── api/      서버 통신
│   └── model/    상태·검증·스키마
├── features/     좋아요·댓글·로그인 (사용자 액션)
├── entities/     user·post·product (업무 개념)
├── widgets/      여러 화면 공용 큰 UI (헤더·탭바)
└── shared/       UI킷·API클라이언트·공용 lib·config

Layers — 영향 범위 (이름 고정, 추가 금지)

위층일수록 책임·의존이 크다. 새 레이어를 만들지 않는 게 규칙 — 의미가 표준화돼 있어야 팀원·AI가 같은 뜻으로 읽기 때문이다.

Slices — 업무 도메인 (이름 자유)

같은 층 안에서 "무슨 일" 기준으로 나눈다. 사진 앱이면 photo·effects, SNS면 post·comments. 핵심 속성: 같은 층의 다른 slice를 모른다(zero coupling). app·shared에는 slice가 없다 — shared는 업무를 모르고, app은 전부 품기 때문이다.

Segments — 기술 목적 (관용 이름)

ui · api · model · lib · config. 이름은 목적(why)으로 짓는다. components·hooks·types·utils 같은 본질(what) 이름은 금지 — 무관한 코드가 한 폴더에 뭉쳐 리팩터링·리뷰가 깨진다. AI가 이런 폴더를 만들려 하면 바로잡을 것.

딱 2대 규칙

규칙 1 — import rule: 위 레이어는 strictly 아래 레이어만 import. 같은 층끼리 금지.
예: features/aaa/api/request.ts는 features/bbb 일체 불가, entities·shared·같은 slice 내부는 가능. 예외 app·shared는 내부 segment끼리 자유.
규칙 2 — public API: slice 바깥은 slice의 index.ts로만 import (내부 구조 직접 참조 금지).
pages/feed/index.ts → export { FeedPage } from "./ui/FeedPage". 바깥 계약만 지키면 내부는 맘대로 뜯어고쳐도 된다. 같은 slice 안은 상대경로 full path, 다른 slice는 절대경로(alias).
entity끼리 알면 @x로 드러내기: entities/A/@x/B.ts ("A crossed with B"). 몰래 import 말고 연결을 눈에 보이게. Entities에서만, 최소 사용. 원문: cross-imports

Public API 심화 — 좋은 계약과 barrel 함정

좋은 public API의 목표 3개: ① 내부 리팩터링으로부터 바깥 보호 ② 행위 변경은 API 변경으로 드러내기 ③ 필요한 것만 노출. export * 와일드카드는 금지 — 인터페이스 파악 불가 + 내부 노출로 리팩터링이 묶인다.

다만 index(barrel) 파일의 실무 함정 4개를 공식이 솔직히 적시한다: 순환 import(같은 slice 안은 상대경로로 회피) · shared/ui·shared/lib 트리쉐이킹 파괴(컴포넌트별 index 분리로 해결) · IDE 자동import가 내부경로를 찍음(Steiger 린터로 단속) · 대규모에서 번들러 성능 저하.

흔한 실수 5

  1. Shared 비대화 — Shared는 계획 말고 개발 중 "진짜 공유되는 것만" 추출. 의존자가 많아 수정 파급이 큼.
  2. 페이지 중복 무리한 추상화 — 복붙은 architecturally wrong이 아님. 단 비즈니스 로직 복붙은 금지.
  3. Feature 남발 — 기준은 '유저 가치 단위', 재사용은 대표 신호. 신입이 pages+features만 봐도 앱 기능이 보여야 함.
  4. export * — slice 인터페이스 파악 불가 + 내부 노출. 필요한 것만 명시 export.
  5. 목적 아닌 이름 — components/utils/hooks 폴더는 세그먼트 목적명으로. shared/lib 잡동사니 금지.

기존 프로젝트 점진 도입 (8단계 요약)

  1. 페이지로 나누기 (route 얇게, page 두껍게 + index.js)
  2. 페이지 외 분리 → shared(페이지가 안 쓰는 것) / app(페이지 쓰는 것·라우트 포함)
  3. 페이지 간 cross-import 제거 (복붙 or shared행)
  4. Shared 털기 (한 화면 전용은 page slice로 — actions·reducers 포함)
  5. 목적별 정리 (components→shared/ui, utils→shared/lib, constants→shared/config)
  6. (선택) 공용 Redux slice → entities(개념) / features(액션)
  7. (선택) modules 폴더 → features or widgets(헤더급)
  8. (선택) shared/ui에서 비즈니스 로직 분리 → 순수 UI킷
팀·매니저 설득 먼저 ("팀원 의사에 반한 전환 금지" — 공식). 셀링 포인트: 점진적이라 새 기능 개발이 중단되지 않음.

React Native / Expo 적용

FSDRN/Expo 대응
app/Expo Router가 app/(src/ 있으면 src/app/까지) 라우팅용으로 점유. 라우트 폴더는 얇은 등록 전용으로 비우고, FSD 전역 app 레이어(프로바이더·전역 설정)는 별도 폴더명 분리 or _layout에 집중. src/ 아래 두기만으로는 해소 안 됨
pages/screen 단위 slice
modelZustand store 자리. RN은 오프라인 캐시·동기화 로직이 entity model에
shared/디자인시스템·fetch 래퍼·딥링크 상수·i18n

bulletproof-react와 차이 (개념 오염 주의)

FSD가 "폴더 존재론"이면 BP는 "라이브러리 처방전" — FSD 뼈대 + BP 도구세트로 병행 가능. 단 한 가지 충돌: index(barrel) 파일. FSD는 캡슐화 계약으로 index.ts를 필수로, BP는 Vite 트리쉐이킹·순환참조 이유로 직접 import를 지향한다. 팀(프로젝트)은 둘 중 하나로 통일할 것. BP 소개 페이지 참조.

AI에게 시킬 말 (복붙용)

"이 레포 FSD import rule 위반 찾아줘 (같은 층·위층 import 목록으로)."
"신규 기능 X를 features/X slice로: ui/api/model + index.ts public API."
"shared 중 한 화면 전용 찾아서 해당 page slice로 옮겨줘."
"components/utils/hooks 폴더 있으면 목적명 세그먼트로 재구성해줘."
