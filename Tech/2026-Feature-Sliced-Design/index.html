Feature-Sliced Design — 폴더 정리의 기술

안녕하세요! 1강에서는 "코드를 어디에 둘까"라는, 생각보다 팀을 많이 아프게 하는 문제를 다룹니다. 끝까지 읽으시면 AI에게 폴더 구조를 지시하고 검수하는 말을 갖게 되실 거예요.

이 강의의 학습목표

① Layers·Slices·Segments를 자기 말로 설명할 수 있다 ② import rule 위반을 눈으로 찾을 수 있다 ③ AI에게 "features/X slice로 만들어줘"라고 지시할 수 있다. 시간은 약 20분, 준비물은 없습니다. 커피 한 잔이면 충분합니다.

30초 요약

  • 코드를 Layers(영향 범위) → Slices(업무 도메인) → Segments(기술 목적) 3겹으로 나눕니다.
  • 프레임워크·언어 무관, 애플리케이션을 만들 때 쓰는 방법론입니다 (라이브러리용 아님).
  • 작은 앱은 app+pages+shared 3층으로 시작하고, 필요할 때 층을 올립니다.
  • 공식 문서의 첫 충고는 의외로 소극적입니다. "멀쩡한 구조는 뜯지 마세요." 새 멤버 적응이 느리거나, 무관한 수정이 연쇄 파손될 때만 도입하는 겁니다.

왜 필요한가요? — PM이 느낄 통증부터

이런 경험 있으시죠? "A 화면 고쳤더니 B 기능이 깨졌다", "신입이 2주째 코드 위치를 못 찾는다", "새 기능 하나에 손댈 곳이 열 군데". 프로젝트가 커지면 폴더는 서랍장처럼 되기 십상입니다. FSD는 서랍장에 라벨링 규칙을 붙이는 일입니다. 코드를 영향 범위(어디까지 파급되나), 업무 도메인(무슨 일용 코드인가), 기술 목적(화면용? 서버용? 설정용?)으로 나눠, 수정의 파급을 눈에 보이게 가둡니다.

🍱 비유 — 도시락 칸나누기: 반찬을 한 통에 섞으면 김치 국물이 달걀말이에 뱁니다. 칸을 나누면(레이어) 반찬끼리(슬라이스) 섞이지 않고, 젓가락이 닿는 면(공개 API)도 정해집니다. FSD가 하는 일이 정확히 이겁니다.

다만 도입에도 비용(학습+마이그레이션)이 듭니다. 상사를 설득할 논리 3개를 공식 문서가 대신 정리해 줬습니다. ① 점진적이라 새 기능 개발이 중단되지 않는다 ② 신입 온보딩이 단축된다 ③ 문서화된 구조라 자체 문서 유지비가 든다 — 아니, 절감된다는 거죠.

3겹 구조 — Layers → Slices → Segments

src/
├── app/          앱 전체 (라우터·프로바이더·전역 설정)
├── pages/feed/   화면 = slice (도메인 단위)
│   ├── ui/       화면 부품        ← segments (목적별)
│   ├── api/      서버 통신
│   └── model/    상태·검증·스키마
├── features/     좋아요·댓글·로그인 (사용자 액션)
├── entities/     user·post·product (업무 개념)
├── widgets/      여러 화면 공용 큰 UI (헤더·탭바)
└── shared/       UI킷·API클라이언트·공용 lib·config

Layers — 영향 범위 (아파트 층수)

위층일수록 책임과 의존이 큽니다. "새 레이어 하나 파죠?"는 금지입니다. 층 이름의 의미가 팀 전체·AI에게 표준으로 통해야 하기 때문입니다. 엘리베이터 버튼과 같아요. 멋대로 층을 추가하면 아무도 못 찾습니다.

Slices — 업무 도메인 (도시락 칸)

같은 층 안에서 "무슨 일" 기준으로 나눕니다. 사진 앱이면 photo·effects, SNS면 post·comments가 되겠죠. 핵심 성질은 같은 층의 다른 slice를 모른다는 겁니다 (zero coupling). 옆집 숟가락을 빌려오지 않는 거예요. 참고로 app·shared에는 slice가 없습니다. shared는 업무 자체를 모르고, app은 전부 품는 층이라 나눌 이유가 없기 때문입니다.

Segments — 기술 목적별 서랍 (관용 이름)

ui · api · model · lib · config가 관용 이름입니다. 여기서 제일 중요한 작명 원칙은 목적(why)으로 짓기입니다. components·hooks·types·utils처럼 "이게 뭐냐(what)"로 지으면, 무관한 코드가 한 폴더에 뭉쳐서 리팩터링할 때 같이 깨집니다. AI가 이런 폴더를 만들려 하면 바로잡아 주세요. "목적이 뭐야?" 한 마디면 됩니다.

딱 2대 규칙 — Import Rule (출입 규칙)

규칙 1 — import rule: 위층은 strictly 아래층만 바라봅니다. 같은 층끼리는 금지.
예: features/aaa/api/request.ts는 features/bbb를 일체 import할 수 없고, entities·shared·같은 slice 내부는 가능합니다. 예외로 app·shared는 내부 segment끼리 자유롭게 참조합니다.
🏢 비유 — 아파트: 윗집이 아랫집에 물건을 빌릴 수는 있지만(아래층 import), 옆집 문을 따고 들어갈 수는 없습니다(같은 층 금지). 옆집 물건이 필요하면 1층 공구함(shared)에 두는 거죠.
규칙 2 — public API: slice 바깥에서는 slice의 index.ts라는 현관문으로만 드나듭니다.
pages/feed/index.ts → export { FeedPage } from "./ui/FeedPage". 현관(계약)만 유지되면, 집 안 구조는 맘대로 뜯어고쳐도 됩니다. 같은 slice 안에서는 상대경로 full path, 다른 slice에서는 절대경로(alias)를 씁니다.
🍽️ 비유 — 식당 메뉴판: 손님은 메뉴판(index.ts)에 있는 것만 주문합니다. 주방 구조가 바뀌어도 메뉴판이 같으면 손님은 모릅니다. export *는 "주방 구경 오세요"나 다름없어서 금지입니다.
식구끼리 알면 @x로 드러내기: entities/A/@x/B.ts ("A crossed with B"). 몰래 드나들지 말고 연결을 눈에 보이게 적습니다. Entities에서만, 최소한으로. 원문: cross-imports

Public API (현관문 규칙) — 좋은 계약과 barrel 함정

좋은 public API의 목표는 세 가지입니다. ① 내부 리팩터링으로부터 바깥을 보호 ② 행위 변경은 API 변경으로 드러내기 ③ 필요한 것만 노출하기. 와일드카드 export *는 "뭐가 메뉴인지 모르겠고, 주방까지 보이는" 상태라 금지입니다.

다만 index(barrel) 파일의 실무 함정 4개를 공식 문서가 솔직하게 적시합니다. 순환 import(같은 slice 안은 상대경로로 회피) · shared/ui·shared/lib 트리쉐이킹 파괴(컴포넌트별 index 분리로 해결) · IDE 자동import가 내부 경로를 찍어버림(Steiger 린터로 단속) · 대규모에서 번들러 성능 저하. "현관문은 필요하지만, 현관문을 너무 많이 만들면 복도가 막힌다"고 이해하시면 됩니다.

Conduit 실습 뜯어보기 — Medium 클론 설계 과정

공식 튜토리얼은 작은 블로그 앱(Conduit)을 처음부터 FSD로 설계합니다. 작은 앱이라 App+Pages+Shared 3층으로 출발합니다. 이 과정 자체가 PM님의 설계 리뷰 체크리스트입니다.

1) 화면 나열 → Pages slice

피드·로그인/가입·글읽기·글쓰기·프로필·설정 — 각 화면이 pages/feed 같은 slice가 됩니다. 핵심은 화면끼리 서로 import 못 함입니다. 화면 간 공유가 필요하면 아래층으로 내립니다.

2) 피드 뜯기 — segments 나누기

태그 목록을 "목록 가져오기(api) + 칩으로 그리기(ui) + 선택 저장(model)"으로 쪼갭니다. 글 목록도 똑같이 api/ui/model입니다. "무슨 화면이냐"가 아니라 "무슨 목적 코드냐"로 나누는 감각, 이게 segments의 전부입니다.

3) Shared는 나중에 추출하기

UI킷·API 래퍼·env 파싱·i18n·라우터 상수 — 개발하면서 "진짜 공유되는 것"만 아래로 내립니다. 헤더 같은 공통 UI도, 윗층(business)을 import하지 않으면 Shared에 둬도 됩니다. 윗층을 참조해야겠다 싶으면 Widgets행입니다.

4) Public API — index.ts 계약 맺기

pages/feed/index.ts
export { FeedPage } from "./ui/FeedPage";

바깥에서는 이 index로만 들어옵니다. Shared는 segment별 index(shared/ui, shared/api…), slice가 있는 층은 slice당 index 1개가 관례입니다.

5) 폼 화면 — model의 일감

글쓰기 화면을 볼까요? 입력·버튼은 Shared에서 가져와 ui에 조립하고, 전송은 api의 mutation이 맡고, 검증 스키마·에러 문구·입력 임시저장은 model이 맡습니다. 리뷰 포인트는 한 줄입니다. "검증은 model에 있나요?"

레이어별 무엇이 들어가나 — 완전 정복

  • Shared (공구함) — 외부 세계와의 접점(백엔드·서드파티·env) + 자체 미니 라이브러리. api(클라이언트+엔드포인트별 함수) · ui(순수 UI킷, 비즈니스 로직 없음 — 로고·레이아웃·검색바 정도는 OK) · lib(날짜·색상 등 영역별, README에 수록 기준 문서화) · config · routes · i18n.
  • Entities (식구들) — user·post 같은 실세계 개념. model(저장·검증 스키마) + api(개체 관련 요청) + ui(여러 화면에서 쓰는 동일 생김새). 개체끼리 얽히면 @x로 드러내고, 로직은 Features/Pages로 올립니다.
  • Features (살림살이) — 유저가 하려는 일 일체. UI(폼) + api + model(검증·내부상태) + config(플래그). 기준은 유저 가치, 재사용은 대표 신호입니다.
  • Widgets (큰 가구) — 여러 화면 공용 큰 블록, 또는 중첩 라우터의 라우터 블록. 한 화면 전용 큰 덩이는 widget으로 올리지 말고 page에 둡니다.
  • Pages (방) — 화면 그 자체 + 로딩·에러바운더리 + 전용 페칭. 전용 model은 드문 편입니다.
  • App (배선) — routes(라우터 설정)·store(전역 store 설정)·styles·entrypoint + 기술적·사업적 전역사(프로바이더·분석).

흔한 실수 5 — 미리 보면 안 합니다

  1. Shared 비대화 — Shared는 계획하지 말고 개발 중 "진짜 공유되는 것만" 추출합니다. 의존자가 많아 수정 파급이 큽니다.
  2. 페이지 중복 무리한 추상화 — 복붙은 architecturally wrong이 아닙니다! 단 비즈니스 로직 복붙은 금지 (버그를 N군데서 고치게 됩니다).
  3. Feature 남발 — 기준은 '유저 가치 단위', 재사용은 대표 신호입니다. 신입이 pages+features만 봐도 앱 기능이 보여야 합니다.
  4. export * — slice 인터페이스 파악 불가 + 내부 노출. 필요한 것만 명시 export 합니다.
  5. 목적 아닌 이름 — components/utils/hooks 폴더는 세그먼트 목적명으로 바꿉니다. shared/lib 잡동사니도 금지입니다.

기존 프로젝트 점진 도입 — 8단계 로드맵

  1. 페이지로 나누기 (route는 얇게, page는 두껍게 + index.js)
  2. 페이지 외 분리 → shared(페이지가 안 쓰는 것) / app(페이지 쓰는 것·라우트 포함)
  3. 페이지 간 cross-import 제거 (복붙 or shared행)
  4. Shared 털기 (한 화면 전용은 page slice로 — actions·reducers 포함)
  5. 목적별 정리 (components→shared/ui, utils→shared/lib, constants→shared/config)
  6. (선택) 공용 Redux slice → entities(개념) / features(액션)
  7. (선택) modules 폴더 → features or widgets(헤더급)
  8. (선택) shared/ui에서 비즈니스 로직 분리 → 순수 UI킷
팀·매니저 설득이 먼저입니다 ("팀원 의사에 반한 전환 금지" — 공식 문서). 셀링 포인트는 하나: 점진적이라 새 기능 개발이 중단되지 않는다는 것!

shared/디자인시스템·fetch 래퍼·딥링크 상수·i18n 그대로입니다

2강 예고 — bulletproof-react와 차이

FSD가 "폴더 존재론"이라면, 다음 강의의 BP는 "라이브러리 처방전"입니다. FSD 뼈대 + BP 도구세트로 병행할 수 있어요. 단 한 가지 충돌이 있습니다. index(barrel) 파일! FSD는 캡슐화 계약으로 index.ts를 필수로 보지만, BP는 Vite 트리쉐이킹·순환참조 이유로 직접 import를 지향합니다. 프로젝트에서는 둘 중 하나로 통일하시면 됩니다. 자세한 건 2강에서요!

AI에게 시킬 말 (복붙용)

"이 레포 FSD import rule 위반 찾아줘 (같은 층·위층 import 목록으로)."
"신규 기능 X를 features/X slice로: ui/api/model + index.ts public API."
"shared 중 한 화면 전용 찾아서 해당 page slice로 옮겨줘."
"components/utils/hooks 폴더 있으면 목적명 세그먼트로 재구성해줘."

Import 실험실 — 눈으로 보는 출입 규칙

같은 그림을 두고 초록불과 빨간불을 비교해 보세요. features/comment의 버튼이 댓글을 그리려 합니다.

✅ features/comment/ui/CommentButton.tsx └─ import { PostCard } from '@/entities/post' ← 아래층, 통과! ❌ features/comment/ui/CommentButton.tsx └─ import { LikeButton } from '@/features/like' ← 옆집 침입, 차단! ❌ entities/post/ui/PostCard.tsx └─ import { addComment } from '@/features/comment' ← 위층 역주행, 차단!
❌ Bad — 옆집·위층 침입
// entities/post/ui/PostCard.tsx
import { addComment }
  from '@/features/comment';
아랫집(entities)이 윗집(features)을 부르면, 위층이 바뀌는 날 아랫집까지 무너집니다.
⭕ Good — 아래층만 바라보기
// features/comment/ui/CommentButton.tsx
import { PostCard }
  from '@/entities/post';
윗집이 아랫집을 쓰는 건 정상입니다. 방향이 한쪽으로만 흐르죠.

PM 리뷰는 쉽습니다. import 줄에 features/xxx에서 features/yyy(xxx≠yyy)가 보이면 빨간불, entities·shared면 초록불입니다.

index.ts가 왜 필요한가요 — 리팩토링 지옥 체험

"매번 index.ts 만들기 귀찮은데요?" — 그 마음, 백 번 이해합니다. 그런데 현관문 없이 살면 이사가는 날 지옥을 봅니다.

❌ Before — 직접 import 3곳
// pages/feed, widgets/sidebar,
// features/search에서 각각:
import { FeedPage }
  from '../pages/feed/ui/FeedPage';
어느 날 ui/FeedPage.tsx를 view/FeedView.tsx로 옮기면? 3곳 전부 고쳐야 합니다. 30곳이면요?
⭕ After — 현관문 하나로
// pages/feed/index.ts (현관문)
export { FeedPage }
  from './view/FeedView';
// 바깥 3곳은 그대로:
import { FeedPage } from '@/pages/feed';
폴더를 뒤집어도 고칠 곳은 index.ts 한 줄입니다. 바깥은 현관 주소만 알면 되니까요.
원문 바로가기: 좋은 public API란

Expo 공존 트리 — 물리적으로 이렇게 둡니다

Expo Router가 app/(src/가 있으면 src/app/까지) 라우팅용으로 점유하므로, FSD의 app 레이어는 src/app이라는 이름을 쓸 수 없습니다. 권장 배치(공식 정답이 아닌 실무 권장 패턴입니다):

expo-project/ ├── app/ ← Expo Router 점유! 라우트 등록 전용 │ ├── _layout.tsx ← 전역 프로바이더 조립 (FSD app 역할) │ ├── index.tsx ← export { FeedPage } from '../src/pages/feed' │ └── article/[slug].tsx ← re-export만, 로직 없음 └── src/ ← FSD 구역 (app 폴더명 사용 금지!) ├── pages/feed/ ← screen slice ├── features/like/ ├── entities/post/ ├── widgets/header/ ├── shared/ └── app-config/ ← FSD app 레이어 대체 (전역 store·스타일)

규칙은 하나입니다. app/에는 로직을 두지 않는다 — 전부 얇은 re-export. 진짜 코드는 src/ 아래 FSD 구역에. 이러면 라우터와 폴더 철학이 충돌 없이 공존합니다.

확인문제 — 1분 퀴즈

Q1. features/like 안의 코드가 features/comment를 import했습니다. 괜찮을까요?
정답 보기안 됩니다. 같은 층(slice)끼리 import 금지! 공용 로직은 아래층(shared 등)으로 내리거나, 조합은 app 레벨에서 하세요.
Q2. 로그인 폼은 한 화면에서만 쓰입니다. features에 둘 수 있을까요?
정답 보기네, 가능합니다. 기준은 '유저에게 가치 있는 일'이지 재사용 횟수가 아닙니다. 재사용은 대표 신호일 뿐이에요.
