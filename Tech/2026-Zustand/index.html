이 강의의 학습목표

① store를 만들고 조각만 구독할 수 있다 ② useShallow가 필요한 경우를 알아본다 ③ persist·devtools를 언제 쓰는지 안다. 약 20분, 곰 인형은 선택 사항입니다.

30초 요약

  • create() 하나로 store를 만들고, useStore(s => s.조각)으로 필요한 조각만 구독합니다. Provider 래핑이 필요 없습니다!
  • Redux와 개념은 유사(불변)하되 보일러플레이트가 없습니다. zombie child·동시성·context loss 문제도 해결돼 있습니다.
  • 셀렉터가 곧 구독입니다. 통째로 구독하면 안 되고, 객체로 묶어 고르면 useShallow를 붙입니다.
  • 서버 상태는 react-query 자리! zustand는 클라이언트 상태만 맡습니다.

최소 코드 — store가 곧 hook입니다

import { create } from 'zustand'

const useBear = create((set) => ({
  bears: 0,
  increase: () => set((s) => ({ bears: s.bears + 1 })),
}))

// 이 조각이 바뀔 때만 다시 그려집니다
const bears = useBear((s) => s.bears)

상태와 액션을 한 store에 같이 두는(colocate) 게 권장 방식입니다. 컴포넌트는 필요한 조각만 선택합니다. 선택한 조각이 바뀔 때만 리렌더되니까요. 반대로 통째로 구독하는 것(useBear())은 "뭐가 바뀌든 전부 다시 그리기"라서 성능 지름길이 됩니다. 자제해 주세요!

🐻 비유 — 곰 우리 관람: 동물원에 가면 보고 싶은 우리(조각)만 봅니다. 매번 동물원 전체(통째 구독)를 한 바퀴 돌 필요는 없죠? 셀렉터가 바로 "보고 싶은 우리만 골라보는" 행위입니다.

병합 규칙 — set은 1레벨만 합쳐줍니다

set은 최상위 1레벨만 얕게 병합합니다. set({ bears: 5 })는 나머지(state 전체)를 유지합니다. 하지만 중첩 객체는 직접 spread로 열어줘야 합니다:

nested: { ...state.nested, count: state.nested.count + 1 }

깊어지면 Immer 미들웨어로 바꿉니다 (set(produce(s => { s.a.b.c++ }))). 전체 교체는 set(next, true)인데, 액션까지 날아가니 최후의 수단입니다. 액션 안에서 현재값이 필요하면 get(), async 액션은 그냥 set 호출 — 특별 취급 없습니다. "준비되면 set"이 전부예요.

비교표 — 왜 Redux 대신인가요?

상대차이선택 기준
Redux개념 유사(불변). Redux는 Provider 필수 + 보일러플레이트가 많음새 프로젝트·소규모 → Zustand. 대규모 규율·DevTools 생태계 → Redux Toolkit
Valtiomutable(proxy) + 접근 기반 자동최적화"막 써도 되게" → Valtio, "명시적으로" → Zustand
Jotai원자(atoms) 조합 vs 단일 store잘게 쪼갠 파생 상태 → Jotai, 기능 단위 store → Zustand
Recoilatom 키 + Provider 필요신규는 비권장 분위기입니다

렌더 최적화는 넷 다 수동 셀렉터가 정석입니다.

핵심 7 — 이건 꼭 가져가세요

  1. 파생값은 계산, 저장 금지: xIsNext = currentMove % 2 (공식 Tic-Tac-Toe 교훈) — 저장하면 동기화가 깨집니다.
  2. Slices 패턴: 큰 store는 createFishSlice+createBearSlice로 나눠 create((...a) => ({...합침})). middleware는 합친 store에만! (slice 안에 걸면 오동작합니다)
  3. 액션 외부화 가능: store 밖에 setState 직접 호출 — hook 없이 호출되고 코드스플리팅에 유리. 캡슐화 취향이면 colocation.
  4. 컴포넌트 밖 읽기/구독: getState()·setState()·subscribe() — 네비게이션 가드·유틸·백그라운드 작업 자리입니다. 단 Next 서버컴포넌트에서는 금지!
  5. 자주 바뀌는 값: subscribe+ref transient 처리로 리렌더 없이 (스크롤·애니메이션 같은 것).
  6. 객체 선택엔 useShallow: useShallow(s => ({nuts, honey})) — 새 객체라 매번 바뀐 걸로 보이는 문제를 해결합니다.
  7. reset은 상수로: initialState 상수 + set(initialState) (로그아웃·세션초기화용).

Tic-Tac-Toe 뜯어보기 — 시간여행이 공짜?!

공식 튜토리얼의 게임 판 + 수 history를 combine(초기상태+액션 분리, TS 추론용)으로 만듭니다:

const useGameStore = create(
  combine({ history: [Array(9).fill(null)], currentMove: 0 },
    (set, get) => ({ setHistory: ..., setCurrentMove: ... })));

수를 두면 history에 판 스냅샷이 추가되고 currentMove가 전진합니다. "몇 수로 돌아가기"는 currentMove만 되돌리면 끝 — 시간여행이 공짜인 거죠! 마지막 정리의 교훈이 압권입니다. xIsNext(다음 차례)는 state에 저장하지 말고 currentMove % 2 === 0으로 계산하세요. 파생값 저장은 동기화 깨짐의 씨앗 — zustand 전체의 제1원칙입니다.

원문 바로가기: Tutorial: Tic-Tac-Toe (전문)

중첩 업데이트 — spread vs Immer

// 기본: 층마다 spread (길지만 명시적)
set((s) => ({ deep: { ...s.deep, nested: {
  ...s.deep.nested, obj: {
    ...s.deep.nested.obj, count: s.deep.nested.obj.count + 1 } } } }));
// Immer: 직접 바꾸듯 씁니다 (프록시가 불변 처리)
set(produce((s) => { s.deep.nested.obj.count++ }));

3층 이상 중첩이 보이면 Immer 미들웨어(zustand/middleware/immer)를 검토하세요. PM 리뷰 멘트: "spread 지옥(5층 이상)이면 Immer 제안해요" — AI가 알아서 쓰겠다고 하면 gotcha 문서부터 확인시키세요.

🧅 비유 — 양파 까기: spread는 양파 껍질을 한 장씩 벗기며 속을 바꾸는 일입니다. 5겹이면 눈물 나죠. Immer는 "그냥 속을 짚어 바꾸면 껍질은 알아서" 해주는 마술 장갑입니다.

useShallow 실예 — 곰들의 식사

const names = useMeals((s) => Object.keys(s));  // 값은 같은데 매번 새 배열 → 리렌더!
const names = useMeals(useShallow((s) => Object.keys(s)));  // 얕게 같으면 스킵!

셀렉터가 객체·배열을 만들어 반환하면(키 목록, 묶음 선택) 내용은 같아도 참조(주소)가 달라서 매번 "바뀌었다"고 판단합니다. useShallow로 감싸면 내용만 비교해서 해결! AI 코드에서 useStore(s => ({a: s.a, b: s.b})) 패턴이 보이면, useShallow 유무가 첫 번째 리뷰 포인트입니다.

📋 비유 — 출석부: 매일 새 출석부를 만들면(새 배열), 이름은 같아도 "다른 문서"로 보입니다. useShallow는 "내용이 같으면 같은 문서로 쳐주는" 도장입니다.
원문 바로가기: Prevent rerenders

persist·구독 실예 — 감싸기 하나면 저장!

import { persist } from 'zustand/middleware';
const useFish = create(persist((set, get) => ({
  fishes: 0,
  addAFish: () => set({ fishes: get().fishes + 1 }),
}), { name: 'food-storage' }));  // localStorage 키

감싸기 하나로 새로고침해도 유지됩니다. RN에서는 저장소만 교체(비동기 주의 — RN 섹션 참조). 컴포넌트 밖에서는 getState/setState/subscribe를 쓰고, subscribeWithSelector 미들웨어로 특정 조각 변경만 구독 + 이전값 비교 + 즉시 발화까지 가능합니다.

TypeScript — 커링 한 겹만 기억하세요

타입 지정 시 커링(currying) 문법인 create<BearState>()(…) 형태로 선언합니다. 괄호가 한 겹 더 있죠? combine을 쓰면 interface 없이 상태·액션을 추론해 줍니다. ExtractState로 테스트·유틸 타입을 재활용하고, 비동기 액션도 타입 그대로 (fetchBears: () => Promise<void>) 씁니다.

미들웨어 4종 — 필요할 때 하나씩

  • persist — 새로고침 유지. { name: '저장키' } + 저장소 교체 가능.
  • devtools — Redux DevTools 연결. set 3번째 인자로 액션명 지정 ("bear/eatFish"처럼).
  • immer — 중첩 업데이트 간편 (zustand/middleware/immer).
  • subscribeWithSelector — 선택 구독 + 이전값 + fireImmediately.

이 넷을 겹쳐 쓰는 게 표준형입니다: create<S>()(devtools(persist(…))). 양파처럼 감싸는 거예요!

테스트 — RNTL까지 공식 지원!

웹 RTL + RN은 RNTL(Native Testing Library) + MSW 조합입니다. store mock으로 테스트마다 setState(initial, true) 리셋 — Jest·Vitest 레시피가 공식 문서에 전문으로 실려 있습니다. 행위 테스트 원칙(구현상세 금지)은 2강 BP와 동일합니다.

React Native 적용 (오해 주의 2건!)

  • RN·웹·바닐라 동일 API입니다. createStore(vanilla)는 React 밖 순수 JS/TS 런타임(이벤트 리스너·서비스·테스트)용 — OS 네이티브 코드(Swift/Kotlin)와 메모리를 공유하는 수단이 아닙니다! (외부 검수에서 잡힌 오해 1호)
  • persist 저장소만 AsyncStorage 어댑터로 교체합니다. 단 AsyncStorage는 비동기(웹 localStorage는 동기!)라서, 앱 시작 시 하이드레이션 대기(스플래시·완료 확인) 없이 쓰면 초기 화면 깜빡임·초기값 덮어쓰기가 납니다. (오해 2호)
  • FSD model/ 세그먼트가 slice 자리입니다. 토큰 저장은 expo-secure-store 등 OS 암호화 저장소 (2강 보안 섹션 참조).

확인문제 — 1분 퀴즈

Q1. const state = useBear()로 통째 구독했더니 화면이 자주 깜빡입니다. 처방은?
정답 보기필요한 조각만 셀렉터로 구독하세요. useBear((s) => s.bears)처럼요. 객체로 묶으면 useShallow까지!
Q2. "장바구니 총액"을 store에 저장하자는 제안, 받아들일까요?
정답 보기안 됩니다! 총액은 단가×수량으로 계산되는 파생값이라 셀렉터 계산이 정답입니다. 저장하면 동기화가 깨집니다.
