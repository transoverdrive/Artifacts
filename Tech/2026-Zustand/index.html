왜 필요한가요? — 30초 상황극

😩 상황극: 로그인한 유저 이름을 보여주려고, 할아버지 컴포넌트 → 아빠 → 나 → 아들 → 손자까지 props를 5단계로 전달하고 있나요? 중간 컴포넌트들은 쓰지도 않는데 그저 통과만 시켜줍니다. 이 고통의 이름이 Props Drilling(프롭스 내리꽂기)입니다.

최소 코드 — 사물함 만들고 화면에 연결하기

import { create } from 'zustand'

// 1. 공용 사물함 만들기: 상태(bears)와 변경 함수(increase)를 한곳에!
const useBearStore = create((set) => ({
  bears: 0,
  increasePopulation: () => set((state) => ({ bears: state.bears + 1 })),
  removeAllBears: () => set({ bears: 0 }),
}))

// 2. 숫자 보여주는 화면: bears가 바뀔 때만 다시 그려집니다
function BearCounter() {
  const bears = useBearStore((state) => state.bears)
  return <h1>곰이 {bears}마리 있습니다.</h1>
}

// 3. 버튼 화면: increase 함수만 꺼내서 onClick에 연결!
function Controls() {
  const increasePopulation = useBearStore((state) => state.increasePopulation)
  return <button onClick={increasePopulation}>한 마리 추가</button>
}

보이시죠? 상태와 액션을 한곳에 모아두고(colocate), 각 화면은 필요한 것만 꺼냅니다. 숫자 화면은 숫자가 바뀔 때만, 버튼 화면은 숫자랑 상관없이 딱 한 번만 그려집니다. 통째로 꺼내는 것(useBearStore())은 "뭐가 바뀌든 전부 다시 그리기"라서 자제해 주세요!

🐻 비유 — 곰 우리 관람: 동물원에 가면 보고 싶은 우리(조각)만 봅니다. 매번 동물원 전체(통째 구독)를 한 바퀴 돌 필요는 없죠? 셀렉터가 바로 "보고 싶은 우리만 골라보는" 행위입니다.

병합 규칙 — set은 1레벨만 합쳐줍니다

set은 최상위 1레벨만 얕게 합쳐줍니다. set({ bears: 5 })는 나머지(state 전체)를 유지합니다. 하지만 중첩 객체는 직접 spread로 열어줘야 합니다:

nested: { ...state.nested, count: state.nested.count + 1 }

전체 교체는 set(next, true)인데, 액션까지 날아가니 최후의 수단입니다. 액션 안에서 현재값이 필요하면 get(), async 액션은 그냥 set 호출 — 특별 취급 없습니다. "준비되면 set"이 전부예요.

원문 바로가기: Immutable & merging · Updating state

중첩 업데이트 — spread vs Immer

// 기본: 층마다 spread (길지만 명시적)
set((s) => ({ deep: { ...s.deep, nested: {
  ...s.deep.nested, obj: {
    ...s.deep.nested.obj, count: s.deep.nested.obj.count + 1 } } } }));
// Immer: 직접 바꾸듯 씁니다 (프록시가 불변 처리)
set(produce((s) => { s.deep.nested.obj.count++ }));

3층 이상 중첩이 보이면 Immer 미들웨어(zustand/middleware/immer)를 검토하세요. PM 리뷰 멘트: "spread 지옥(5층 이상)이면 Immer 제안해요!"

🧅 비유 — 양파 까기: spread는 양파 껍질을 한 장씩 벗기며 속을 바꾸는 일입니다. 5겹이면 눈물 나죠. Immer는 "그냥 속을 짚어 바꾸면 껍질은 알아서" 해주는 마술 장갑입니다.

useShallow 실예 — 곰들의 식사

const names = useMeals((s) => Object.keys(s));  // 값은 같은데 매번 새 배열 → 리렌더!
const names = useMeals(useShallow((s) => Object.keys(s)));  // 얕게 같으면 스킵!

셀렉터가 객체·배열을 만들어 반환하면(키 목록, 묶음 선택) 내용은 같아도 참조(주소)가 달라서 매번 "바뀌었다"고 판단합니다. useShallow로 감싸면 내용만 비교해서 해결! AI 코드에서 useStore(s => ({a: s.a, b: s.b})) 패턴이 보이면, useShallow 유무가 첫 번째 리뷰 포인트입니다.

📋 비유 — 출석부: 매일 새 출석부를 만들면(새 배열), 이름은 같아도 "다른 문서"로 보입니다. useShallow는 "내용이 같으면 같은 문서로 쳐주는" 도장입니다.

Tic-Tac-Toe 뜯어보기 — 액션 속을 다 보여드립니다

공식 튜토리얼의 게임 판 + 수 history를 combine(초기상태+액션 분리, TS 추론용)으로 만듭니다. 지난번엔 생략했던 액션 내부를 이번엔 전부 공개합니다:

const useGameStore = create(
  combine({ history: [Array(9).fill(null)], currentMove: 0 },
    (set, get) => ({
      // history에 새 판 스냅샷 추가 (함수 or 값 둘 다 받음)
      setHistory: (nextHistory) => {
        set((state) => ({
          history: typeof nextHistory === 'function'
            ? nextHistory(state.history) : nextHistory,
        }))
      },
      // 현재 수만 전진! 이 한 줄이 시간여행의 전부
      setCurrentMove: (nextCurrentMove) => {
        set((state) => ({
          currentMove: typeof nextCurrentMove === 'function'
            ? nextCurrentMove(state.currentMove) : nextCurrentMove,
        }))
      },
    })));

// 수를 두면: history 추가 + currentMove 전진
function handlePlay(nextSquares) {
  const nextHistory = [...history.slice(0, currentMove + 1), nextSquares]
  setHistory(nextHistory)
  setCurrentMove(nextHistory.length - 1)
}
// "3수 전으로": currentMove만 3으로! 판은 history[3]이 그대로
function jumpTo(nextMove) { setCurrentMove(nextMove) }

느끼셨죠? "몇 수로 돌아가기"는 currentMove 숫자 하나만 되돌리면 끝 — 판 스냅샷이 history에 다 있으니까요. 그래서 시간여행이 공짜입니다. 마지막 정리의 교훈: xIsNext(다음 차례)는 state에 저장하지 말고 currentMove % 2 === 0으로 계산하세요. 파생값 저장은 동기화 깨짐의 씨앗 — zustand 전체의 제1원칙입니다.

비동기라서: 다 읽을 때까지 기다리기 (공식 해법!)

AsyncStorage는 Promise라서, 앱이 먼저 켜지고 데이터가 나중에 도착합니다. 공식 해법 두 가지:

// 해법 A: 다 읽히면 알려주는 리스너
onRehydrateStorage: (state) => {
  console.log('hydration starts')  // 읽기 시작!
  return (state, error) => {
    if (error) { console.log('읽기 실패', error) }
    else { console.log('hydration finished') }  // 다 읽힘!
  }
}

// 해법 B: 내가 원할 때 직접 다시 읽기 (예: 앱 시작 후)
skipHydration: true,  // 자동 읽기를 끄고…

// 화면에서:
useEffect(() => { useBoundStore.persist.rehydrate(); }, [])
// ↑ 마운트 후에 직접 읽기 시작. 스플래시 보여주다 완료되면 넘어가면 됩니다!

컴포넌트 밖에서는 getState/setState/subscribe를 쓰고, subscribeWithSelector로 특정 조각 변경만 구독할 수 있습니다.

TypeScript — 왜 괄호가 두 개일까요?

타입 지정 시 create<BearState>()(…) — 괄호가 한 겹 더 있죠? 당황하셨죠? 이유는 이렇습니다. TypeScript가 일부 타입(상태 모양)만 수동으로 받고 나머지는 자동 추론하게 하려는 문법적 우회책입니다. 공식 문서도 "그냥 create<타입>()(…) 공식을 외워서 쓰라"고 권장합니다. 원리를 찾느라 헤매지 마세요, 외우는 게 정답인 구간입니다!

combine을 쓰면 interface 없이 상태·액션을 추론해 줍니다. ExtractState로 테스트·유틸 타입을 재활용하고, 비동기 액션도 타입 그대로 (fetchBears: () => Promise<void>) 씁니다.

실무 팁 — 자동 셀렉터 생성

매번 (s) => s.bears 화살표 함수를 쓰기 귀찮죠? 공식 문서의 createSelectors 유틸을 한 번 감싸면, 이후엔 이렇게 꺼내 씁니다:

// 감싸기 한 번:
const useBearStore = createSelectors(useBearStoreBase)

// 이후엔 화살표 함수 없이!
const bears = useBearStore.use.bears()       // 값 꺼내기
const increment = useBearStore.use.increment() // 액션 꺼내기

SSR 주의 — 서버에서는 사물함을 따로!

Next.js 같은 서버 렌더링에서는 모듈 전역 store를 그대로 쓰면 다른 사용자들의 요청이 같은 사물함을 공유해서 상태가 섞일 수 있습니다. 그래서 요청마다 별도 store(vanilla createStore + Context로 주입, 초기값은 props에서)를 쓰는 게 정석입니다. 레포 README의 "React context" 섹션이 바로 이 패턴입니다. 자세한 서버 패턴은 공식 SSR 가이드를 참조하세요. (수집 시 해당 페이지 접근 실패로 원문은 미보관 — 링크로 대체합니다.)

React Native 적용 (오해 주의 2건!)

  • RN·웹·바닐라 동일 API입니다. createStore(vanilla)는 React 밖 순수 JS/TS 런타임(이벤트 리스너·서비스·테스트)용 — OS 네이티브 코드(Swift/Kotlin)와 메모리를 공유하는 수단이 아닙니다!
  • persist 저장소는 위 persist 실전의 교체+대기 패턴 그대로 (AsyncStorage + onRehydrateStorage/skipHydration).
  • FSD model/ 세그먼트가 slice 자리입니다. 토큰 저장은 expo-secure-store 등 OS 암호화 저장소 (2강 보안 섹션 참조).

웹 RTL + RN은 RNTL(Native Testing Library) + MSW(가짜 서버) 조합입니다. store mock으로 테스트마다 setState(initial, true) 리셋 — Jest·Vitest 레시피가 공식 문서에 전문으로 실려 있습니다. 행위 테스트 원칙(구현상세 금지)은 2강 BP와 동일합니다.

// Slices: 큰 사물함을 칸막이로! (물고기칸 + 곰칸 합치기)
export const createFishSlice = (set) => ({
  fishes: 0,
  addFish: () => set((state) => ({ fishes: state.fishes + 1 })),
})
export const createBearSlice = (set) => ({
  bears: 0,
  addBear: () => set((state) => ({ bears: state.bears + 1 })),
  eatFish: () => set((state) => ({ fishes: state.fishes - 1 })),
})
export const useBoundStore = create((...a) => ({
  ...createBearSlice(...a),
  ...createFishSlice(...a),
}))  // ※ middleware(persist 등)는 여기 합친 곳에만!

// Reset: 로그아웃·세션 초기화용
const initialState = { bears: 0, food: 'honey' }
const useBearStore = create()((set) => ({
  ...initialState,
  reset: () => set(initialState),  // 한 줄로 원복!
}))

비교표 — 왜 Redux 대신인가요? (복습 겸)

상대차이선택 기준
Redux개념 유사(불변). Redux는 Provider 필수 + 복잡한 설정 코드가 많음새 프로젝트·소규모 → Zustand. 대규모 규율·DevTools 생태계 → Redux Toolkit

확인문제 — 1분 퀴즈

Q1. const state = useBearStore()로 통째로 꺼냈더니 화면이 자주 깜빡입니다. 처방은?
정답 보기필요한 조각만 셀렉터로 꺼내세요. useBearStore((s) => s.bears)처럼요. 객체로 묶으면 useShallow까지!
Q2. "장바구니 총액"을 store에 저장하자는 제안, 받아들일까요?
정답 보기안 됩니다! 총액은 단가×수량으로 계산되는 파생값이라 셀렉터 계산이 정답입니다. 저장하면 동기화가 깨집니다.
Q3. RN에서 로그인을 유지하려고 persist + AsyncStorage를 달았더니 첫 화면이 깜빡입니다. 왜죠?
정답 보기AsyncStorage는 비동기라 데이터가 늦게 도착합니다. onRehydrateStorage로 완료를 받거나 skipHydration + rehydrate()로 읽기 시점을 직접 잡으세요. (persist 실전 섹션!)
