왜 필요한가요 — "bulletproof" 9원칙

React의 가장 큰 장점(자유도)이 가장 큰 단점이기도 합니다. 팀마다 구조가 다르고, "뭘 써야 하죠?"라는 질문에 답이 수백 개입니다. 이 레포의 제안은 단순합니다. "실전에서 가장 잘 먹힌 조합을 고정하자." 쉽게 시작 · 이해·유지보수 용이 · 적재적소 도구 · 깨끗한 경계 · 팀 컨벤션 일치 · 보안 · 성능 · 코드·팀 규모 확장성 · 그리고 문제의 조기 발견(타입·린트·테스트로 일찍 잡기).

💊 비유 — 처방전: 감기에 걸리면 약국에 약이 수백 개지만, 의사는 증상에 맞는 3가지를 처방합니다. 이 레포가 그 처방전이고, 데모앱이 복약 지도입니다. 약(라이브러리)은 바꿔도 되고, 복용법(원칙)이 핵심입니다.

샘플앱(팀·토론·댓글, ADMIN/USER 역할)은 Vite·Next App·Next Pages 3종으로 구현돼 있습니다. 꼭 뜯어보세요. 읽는 것만으로 감이 옵니다.

폴더 뼈대 — features가 본진입니다

src/
├── app/           routes·app.tsx·provider·router
├── components/    전역 공용
├── config/        전역 설정·env
├── features/      ★ auth·discussions·comments…
│   └── awesome/
│       ├── api · components · hooks
│       └── stores · types · utils (필요한 것만!)
└── hooks·lib·stores·testing·types·utils·assets

확장성의 비결은 한 줄입니다. "기능 코드를 공용이랑 섞지 마라." feature 안 폴더는 필요한 것만 만듭니다. 1인 가구 냉장고에 반찬 통을 기능별로 두는 거예요. API 호출이 기능 간에 많이 겹치면 별도 api 폴더로 빼는 것도 허용됩니다. 융통성이 있다는 얘기죠.

두 강제 장치 (ESLint): ① cross-feature import 금지 — 기능끼리 직거래 금지, 조합은 app 레벨에서. ② 단방향 shared → features → app — 거꾸로 흐르면 에러. 코드가 한 방향으로만 흘러야 예측 가능합니다.

컴포넌트 — 합성이 정답입니다

  • 쓰는 곳 곁에 두기(colocation) — 가까울수록 읽기 쉽고, 불필요한 리렌더도 줄어 성능까지 좋아집니다. 일석이조죠.

API 3단 뜯어보기 — discussions 실예

공식 권장 패턴 그대로입니다. 타입 → fetcher → react-query 훅:

// api/get-discussions.ts
export const getDiscussions = (params): Promise<Discussion[]> => {
  return api.get('/discussions', { params });
};

export const useDiscussions = (params) => {
  return useQuery({
    queryKey: ['discussions', params],
    queryFn: () => getDiscussions(params),
  });
};

포인트 3개입니다. ① 단일 api-client 인스턴스 공유 (fetch든 axios든 상관없음) ② 요청 선언을 그때그때 만들지 않고 파일로 고정 → 목록이 보인다 ③ 응답 타입이 아래로 추론. PM 리뷰는 쉽습니다. "새 API인데 타입·fetcher·훅 3단이 있나요?" 이것만 물어보세요.

ESLint 강제 — 규칙을 사람에게 맡기지 않는다

cross-feature 금지는 구호가 아니라 린트 규칙입니다 (import/no-restricted-paths zones):

'import/no-restricted-paths': ['error', { zones: [
  { target: './src/features/auth', from: './src/features', except: ['./auth'] },
  // ...comments·discussions·teams·users 동일
  { target: './src/features', from: './src/app' },  // 단방향 강제
]}]

이게 BP의 핵심 철학입니다. "구조는 문서가 아니라 빌드가 지킨다." AI가 구조를 깨는 코드를 내면 커밋 전 Husky+ESLint가 차단합니다. PM님은 "이 규칙이 켜져 있나요?" 이것만 확인하시면 됩니다.

children 최적화 — 코드로 이해하기

// 미최적: count가 바뀔 때마다 PureComponent도 같이 리렌더
const Counter = () => {
  const [count, setCount] = useState(0);
  return (<div><button onClick={...}/><PureComponent /></div>);
};
// 최적: children은 부모 리렌더에 영향 안 받음!
const App = () => (<Counter><PureComponent /></Counter>);
const Counter = ({ children }) => {
  const [count, setCount] = useState(0);
  return (<div><button onClick={...}/>{children}</div>);
};

JSX를 children으로 넘기면 고립된 VDOM이 돼서, 부모가 다시 그려도 따라 그려지지 않습니다. memo·useMemo 꺼내기 전에 쓸 치트키죠. AI 리뷰 포인트도 쉽습니다. "상태 쓰는 컴포넌트 안에, 상태 안 쓰는 무거운 자식이 같이 있나요?"

테스트 — 통합 중심 피라미드

  • 통합 테스트가 본진입니다 (unit 통과 ≠ 연결 보장). unit은 공용·복잡로직만, e2e는 핵심 여정만.

보안 — 웹 기준 + RN 주의보

  • 인증: SPA는 JWT가 대세. 저장은 HttpOnly 쿠키 권장 (localStorage는 XSS 탈취 위험!). 입력 sanitize는 필수입니다. 참고: OWASP 클라이언트 리스크 Top 10.
  • 인가: RBAC(역할: USER/ADMIN) + PBAC(세밀 정책: "작성자만 삭제" 같은 것). 클라이언트 인가는 UX용 — 서버 검증이 진짜입니다. 이 순서 꼭 기억하세요!
  • ⚠️ React Native는 다릅니다: RN은 브라우저 쿠키 환경이 아니라서 HttpOnly 자동관리가 웹처럼 동작하지 않습니다. 토큰은 expo-secure-store·keychain 같은 OS 암호화 저장소에 보관 후 헤더로 전송하는 게 표준입니다.

성능 — children이 치트키입니다

  • 라우트 단위 코드스플리팅 (과하면 요청 폭증 — 균형이 생명).
  • 상태 분할 + 쓰는 곳 곁에 두기. 비싼 초기값은 initializer 함수로 1회만 계산.
  • children prop이 가장 쉬운 최적화 — 부모 리렌더가 자식 VDOM을 안 건드립니다.

  • 이미지 lazy+WebP+srcset, Web Vitals(Lighthouse) 주시, react-query prefetch로 선로딩.

React Native 적용 — BP 용어로 매핑하기

공식은 "같은 구조를 React Native에 적용 가능"이라고 합니다. app/=네비게이션·프로바이더, features는 동일합니다. RN 추가분은 BP 용어로 이렇게 매핑하세요. 오프라인 캐시는 feature stores/서버캐시, 푸시·딥링크는 config, 네이티브 모듈은 lib에 넣습니다. (FSD의 entity/model 용어를 섞지 마세요 — BP에는 그 개념이 없습니다!) Expo Router 사용 시 BP의 src/app도 라우터 예약 폴더와 충돌하므로 라우트 등록 전용으로 분리합니다.

FSD와 차이 — barrel 논쟁 정리

※ FSD(캡슐화 우선, index.ts 필수)와 달리, BP는 번들 최적화(Vite 트리쉐이킹)·순환참조 회피를 위해 barrel 없는 직접 import를 지향합니다. 옛 권장(배럴 사용)은 개정된 겁니다. 프로젝트에서는 둘 중 하나로 통일하세요. 제1강 FSD에서 뼈대를 복습하실 수 있습니다.

확인문제 — 1분 퀴즈

Q1. 새로 만든 API가 컴포넌트 안에서 직접 fetch를 호출합니다. BP 기준으로 뭐가 빠졌나요?
