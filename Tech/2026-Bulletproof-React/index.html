왜 필요한가 — "bulletproof" 9원칙

React는 자유도가 너무 커서 팀마다 구조가 다르고, 선택지가 수백 개라 압도당한다. 이 레포는 "실전에서 가장 잘 먹힌 조합"을 고정해 준다: 쉽게 시작 · 이해·유지보수 용이 · 적재적소 도구 · 깨끗한 경계 · 팀 컨벤션 일치 · 보안 · 성능 · 코드·팀 규모 확장성 · 문제의 조기 발견(타입·린트·테스트로 일찍 잡기).

샘플앱(팀·토론·댓글, ADMIN/USER 롤)은 Vite·Next App·Next Pages 3종으로 구현돼 있어 뜯어보며 배우게 돼 있다.

폴더 뼈대 — features가 본진

src/
├── app/           routes·app.tsx·provider·router
├── components/    전역 공용
├── config/        전역 설정·env
├── features/      ★ auth·discussions·comments…
│   └── awesome/
│       ├── api · components · hooks
│       └── stores · types · utils (필요한 것만)
└── hooks·lib·stores·testing·types·utils·assets

확장성 비결은 "기능 코드를 공용과 섞지 않는다"이다. feature 안 폴더는 필요한 것만 만든다. API 호출이 기능 간에 많이 겹치면 별도 api 폴더로 빼는 것도 허용.

두 강제 장치 (ESLint): ① cross-feature import 금지 — 조합은 app 레벨에서. ② 단방향 shared → features → app — 거꾸로 금지. 코드가 한 방향으로만 흘러야 예측 가능하다.

프로젝트 표준 — 품질의 자동화

  • ESLint — 실수 조기 발견 + 컨벤션 강제 (파일명 kebab-case까지 규칙으로).
  • Prettier + 저장 시 자동포맷 — 포맷 실패 자체가 문법 오류 신호.
  • TypeScript — 대규모 리팩터링의 안전망. 요령: 타입 선언부터 고치고 에러를 따라가라. 단 런타임 실패까지 막진 못함.
  • Husky git hooks — 커밋 전 린트·포맷·타입체크. 나쁜 커밋은 원천 차단.
  • Absolute imports (@/) — ../../../ 지옥 탈출. 파일 이동해도 import 유지.

컴포넌트 — 합성이 정답

  • 쓰는 곳 곁에 두기(colocation) — 가까울수록 가독성+성능(불필요 리렌더 감소).
  • 내부 렌더 함수 중첩 금지 — UI 단위는 별도 컴포넌트로 추출.
  • props 개수 제한 — 많으면 분할 or children/slots 합성.
  • 공용 컴포넌트는 라이브러리화 (3rd-party도 래핑 — 교체 비용 절감). 반복 확인 전 추상화 금지.
  • 선택지: 완성형(Chakra·Mantine·MUI·AntD) vs 헤드리스(Radix·Base UI·Headless·react-aria) vs 코드형(ShadCN·Park). 스타일링: tailwind·vanilla-extract·Panda·CSS modules·styled·emotion. Storybook으로 격리 개발·카탈로그화.

API 레이어 3단

테스트 — 통합 중심 피라미드

  • 통합 테스트가 본진 (unit 통과 ≠ 연결 보장). unit은 공용·복잡로직만, e2e는 핵심 여정만.
  • Vitest(빠른 Jest) + Testing Library(행위 테스트, 구현상세 금지 — 상태관리 갈아끼워도 테스트 유지) + Playwright(브라우저/헤드리스).
  • MSW — 백엔드 없이 진짜 HTTP로 프론트 개발·테스트. API 설계용으로도 씀.

에러 — 3층 방어

  • API 인터셉터 — 토스트 알림·401 토큰갱신·미인증 로그아웃.

  • Sentry + 소스맵 — 프로덕션 추적 (플랫폼·브라우저별).
원문 바로가기: Error Handling

보안 — 웹 기준 + RN 주의

  • 인증: SPA는 JWT. 저장은 HttpOnly 쿠키 권장 (localStorage는 XSS 탈취 위험). 입력 sanitize 필수. 참고: OWASP 클라이언트 리스크 Top 10.
  • 인가: RBAC(역할: USER/ADMIN) + PBAC(세밀 정책: "작성자만 삭제" 등). 클라이언트 인가는 UX용 — 서버 검증 필수.
  • ⚠️ React Native는 다름: RN은 브라우저 쿠키 환경이 아니라 HttpOnly 자동관리가 웹처럼 동작하지 않는다. 토큰은 expo-secure-store·keychain 같은 OS 암호화 저장소에 보관 후 헤더 전송이 표준.
원문 바로가기: Security — RBAC/PBAC 예제 코드

성능 — children이 치트키

  • 라우트 단위 코드스플리팅 (과하면 요청 폭증 — 균형).
  • 상태 분할 + 쓰는 곳 곁에. 비싼 초기값은 initializer 함수로 1회만.
  • children prop이 가장 쉬운 최적화 — 부모 리렌더가 자식 VDOM을 안 건드림.
  • 고빈도 상태는 context 말고 셀렉터 내장 상태관리(zustand·jotai). 잦은 업데이트 앱은 runtime 스타일→zero-runtime.
  • 이미지 lazy+WebP+srcset, Web Vitals(Lighthouse) 주시, react-query prefetch.

AGENTS.md — AI에게 그대로 먹이기

레포에 AI 코딩 에이전트용 지시서가 동봉돼 있다. 기능 개발 4단계(API 타입 → fetcher+훅 → UI → 통합테스트 → 라우팅), 컴포넌트는 Plop 제너레이터, Husky pre-commit·pre-push. 표준 스택: React 18 + TS strict + Tailwind + Radix + TanStack Query + Zustand + Vitest/Playwright/MSW/Storybook.

원문 바로가기: AGENTS.md 전문 · 추가 학습 Additional Resources

React Native 적용 (BP 용어로 매핑)

공식: "같은 구조를 React Native에 적용 가능". app/=네비게이션·프로바이더, features 동일. RN 추가분은 BP 용어로: 오프라인 캐시는 feature stores/서버캐시, 푸시·딥링크는 config, 네이티브 모듈은 lib에 (FSD의 entity/model 용어를 섞지 말 것 — BP에는 그 개념이 없음). Expo Router 사용 시 BP의 src/app도 라우터 예약 폴더와 충돌하므로 라우트 등록 전용으로 분리.

FSD와 차이 — barrel 논쟁

※ FSD(캡슐화 우선, index.ts 필수)와 달리, BP는 번들 최적화(Vite 트리쉐이킹)·순환참조 회피를 위해 barrel 없는 직접 import를 지향한다. 옛 권장(배럴)은 개정됨. 프로젝트는 둘 중 하나로 통일. FSD 소개 페이지 참조.

API 3단 뜯어보기 — discussions 실예

공식 권장 패턴 그대로다. 타입 → fetcher → react-query 훅:

// api/get-discussions.ts
export const getDiscussions = (params): Promise<Discussion[]> => {
  return api.get('/discussions', { params });
};

export const useDiscussions = (params) => {
  return useQuery({
    queryKey: ['discussions', params],
    queryFn: () => getDiscussions(params),
  });
};

포인트 3개: ① 단일 api-client 인스턴스 공유 (fetch·axios 무관) ② 요청 선언을 그때그때 만들지 않고 파일로 고정 → "우리 앱의 엔드포인트 목록"이 코드로 보인다 ③ 응답 타입이 아래로 추론. PM 리뷰: "새 API인데 타입·fetcher·훅 3파일(또는 3단)이 있나"만 보면 된다.

ESLint 강제 — 규칙을 사람에게 맡기지 않는다

cross-feature 금지는 구호가 아니라 린트 규칙이다 (import/no-restricted-paths zones):

'import/no-restricted-paths': ['error', { zones: [
  { target: './src/features/auth', from: './src/features', except: ['./auth'] },
  // ...comments·discussions·teams·users 동일
  { target: './src/features', from: './src/app' },  // 단방향 강제
]}]

이게 BP의 핵심 철학이다 — "구조는 문서가 아니라 빌드가 지킨다". AI가 구조를 깨는 코드를 내면 커밋 전 Husky+ESLint가 차단한다. PM은 "이 규칙이 켜져 있나"만 확인하면 된다.

children 최적화 — 코드로 이해하기

// 미최적: count 바뀔 때마다 PureComponent도 리렌더
const Counter = () => {
  const [count, setCount] = useState(0);
  return (<div><button onClick={...}/><PureComponent /></div>);
};
// 최적: children은 부모 리렌더에 영향 안 받음
const App = () => (<Counter><PureComponent /></Counter>);
const Counter = ({ children }) => {
  const [count, setCount] = useState(0);
  return (<div><button onClick={...}/>{children}</div>);
};

JSX를 children으로 넘기면 고립된 VDOM이 돼 부모가 다시 그려도 안 따라 그려진다. memo·useMemo 이전에 쓸 치트키. AI 리뷰 포인트: "상태 쓰는 컴포넌트 안에 안 쓰는 무거운 자식이 같이 있나".
